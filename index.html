CASE FILE AI appointment setter

We added one question.
The setter lost its memory.

SYMPTOM 1

Re-asks questions the lead already answered

SYMPTOM 2

Skips its intro message

Two symptoms from one change usually mean one root cause: the bot no longer knows where the lead is in the flow.

01 How a setter thinks

Every single message runs this loop

The LLM has no memory of its own. It only knows what we hand it in step 3. If steps 2 or 3 go wrong, it's guessing.

03 Likely cause A · the data layer

Answers are tracked by position, not by name

Lots of setters store progress as "step 2". Insert a question at the top and every number shifts. The saved pointer now lands on the wrong question.

🧍 Sarah (mid-conversation)
saved: current_step = 2
Step 2 → Timeline. Budget already answered ✓
🆕 Brand-new lead
starts at: current_step = 0
Step 0 → Intro ✓
03b Same layer, second way it breaks

The answer is said, but never saved

After each lead message, an extraction step turns text into fields. Adding a question changes its schema. If the parser fails silently, it saves nothing and the prompt says "known: nothing".

1. Lead says

"Staying consistent.
Budget's about $200/mo btw"
→

2. Extractor returns

// expects: {budget, timeline}
{ "biggest_challenge": "consistency",
  "Budget": "$200/mo" }
→

3. Saved to memory

// waiting…
04 Likely cause B · the prompt layer

The new line overrides the old rules

The question gets pasted in as "FIRST, ask…". LLMs follow the most specific, most direct instruction. The prompt also gets longer, so old messages get cut off to fit the token limit.

System prompt

FIRST: ask "What's your biggest challenge?" Then ask budget, timeline, decision maker, in order.
1. Always open with the intro message.
2. Check what's already known. Never re-ask.
3. Qualify: budget → timeline → decision maker.
4. When qualified, send the booking link.

What fits in the context window

05 What I check first

Stop the damage. Then X-ray one bad turn.

Open the exact request sent to the LLM on one broken reply. Three questions tell you which cause it is.

messages: [ …only the last 2 turns… ] known_fields: { budget: null, timeline: null } current_step: 2 → "budget" system: "FIRST: ask biggest challenge… / Always open with intro…"
06 The fix

Take memory away from the LLM. Give it to code.

The LLM should write the message. Code should decide what's known and what's next.

1

Name questions with stable IDs

BEFORE
current_step = 2
answer_1 = "$200"
AFTER
answers.budget = "$200/mo"
answers.timeline = null
# adding a question never shifts anything
2

Code works out what's left and tells the LLM

BEFORE
"Ask these questions in order:
 budget, timeline, decision maker"
AFTER
KNOWN: budget=$200/mo, challenge=consistency
STILL NEEDED: timeline   ← only this one
Never ask for anything under KNOWN.
3

Make the intro a coded step, not an LLM choice

BEFORE
Prompt: "Always open with the intro"
(can be overridden by any new line)
AFTER
if not lead.intro_sent:
    send(INTRO_TEMPLATE)
    lead.intro_sent = True
4

Make extraction fail loudly, and migrate live leads

BEFORE
try: parse(json)
except: save({})   # silent
AFTER
validate against schema → on fail: retry + alert
map old saved state → new IDs for
every lead already mid-conversation
always keep full history in the token budget
07 The system

Every change passes 6 gates before a client sees it

Try shipping the exact change that broke things, then a good one.

📝

Version + PR

Prompt & questions in git. Reviewed diff.

🎬

Replay tests

50 real chats, cut at every stage

🧪

Mid-flow tests

Leads already halfway when the change lands

👻

Shadow mode

New bot drafts replies on live traffic, sends nothing

🐤

Canary 10%

One client or 10% of leads for 24h

📡

Monitor + auto-rollback

Metrics drift → old version back

🎬 What the replay tests check

  • Hard checks: intro on turn 1
  • Hard checks: 0 questions about filled fields
  • Hard checks: all required fields collected, booking link sent
  • LLM judge: tone, natural flow, on-brand
  • Any fail = deploy blocked

📡 What we watch live

  • Re-ask rate (bot asks for a field that's already filled)
  • Intro-sent rate on first message
  • Drop-off per question
  • Booking rate vs last version
  • Off by >X% in 24h → auto-rollback + alert

🔒 Rules for every change

  • Questions = data rows, not prompt prose
  • Question list edited → mid-flow tests run automatically
  • New fields → schema + migration in the same PR
  • Rollback = one click, practiced
  • Every failed live chat → becomes a new replay test
